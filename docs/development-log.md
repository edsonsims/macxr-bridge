# MacXR Bridge — research and plan (Nov 7, 2026)

Goal (Edson): a macOS equivalent of Meta Quest Link on Windows: press Play in the Unity Editor → the app shows up on the Quest 3 with real tracking, hands and passthrough.
Decision (Nov 7): **our own fork**, built on OXRSys. Renamed on Nov 8 from its Portuguese working name to **MacXR Bridge**, a neutral name ("Link" is a Meta trademark).

## Facts
- Meta does not offer Quest Link on macOS (Unity Link doc, Apr 2026: "Link is currently only supported on Windows"). Parallels/Windows on ARM can't run Quest Link; Boot Camp doesn't exist on Apple Silicon.
- **OXRSys** (formerly OpenXR OSX), by Yannick Comte (demonixis): https://github.com/demonixis/oxrsys
  - MPL-2.0; 114 stars, 10 contributors; 1.3.0 released on Nov 4, 2026.
  - Native OpenXR runtime for macOS in C++20; Metal (`XR_KHR_metal_enable`) and Vulkan via MoltenVK; VideoToolbox H.264/H.265 encoder (HEVC Main10 negotiated).
  - Transport: USB via `adb reverse` (ports 9944/9945/9946; 9948 "spatial" reserved but not implemented) or Wi-Fi UDP; 1.3.0 adds USB CDC-NCM.
  - Android Quest/Pico client (MediaCodec, ~11 ms H.264 decode); Vision Pro client; macOS simulator; SwiftUI "Home" app (runtime selection, ADB, diagnostics). The client is installed by sideloading (`./gradlew assembleDebug` + `adb install`).
  - Runtime selection: `oxrsys-runtime.json` via `XR_RUNTIME_JSON` or `~/.config/openxr/1/active_runtime.json`; config in `~/Library/Application Support/OXRSys/oxrsys-runtime.toml`.
  - Already has: hands (`XR_EXT_hand_tracking` coming from the Quest client), passthrough (`XR_FB_passthrough` on the client; real alpha packed below the eyes, 1.3.0), foveation, quad/cylinder layers composited before encoding, Unity package `net.demonixis.oxrsys-unity` (runtime selection in the Editor).
  - Missing: scene/anchors (`XR_FB_scene`, `XR_FB_spatial_entity`), Quest camera (PCA), microgestures, audio (skeleton only), validation with the Meta XR SDK (OVRPlugin) on the Mac.
- MRUK has `SaveSceneToJsonString()` and `LoadSceneFromJsonString()` (`Json` data source), which lets the Editor use the real room without runtime support.
- Meta XR Simulator Data Forwarding only forwards Touch controllers (not hands or head).

## What the Hello World needs from the bridge
| Need | OXRSys today | For the competition |
|---|---|---|
| Play Mode → headset, head tracking | yes | use |
| Hands and pinch (ISDK) | yes | use |
| Passthrough with labels on top | yes (validate with `OVRPassthroughLayer`) | validate on day 1 |
| Quest camera (PCA) for object detection | no | Editor: Mac webcam or recorded frames; real camera only in the build |
| Room (MRUK) | no | export JSON on the headset once, load it in the Editor |
| Depth (`EnvironmentRaycastManager`) | no | raycast against the MRUK planes in the Editor |
| Microgestures | no | keyboard in the Editor; real in the build |
| Persistent anchors | no | build only |
| Microphone/audio | no | Mac mic and speakers in the Editor |
| Meta XR SDK 207 (OVRPlugin) on the Mac | untested | **risk #1**: test on day 1 |

## Nov 8 (early morning) — RISK #1 SOLVED: Meta XR SDK 207 runs on the Mac runtime and the Quest 3 receives Play Mode
Tools built to test without touching the screen: `macxr-bridge/unity-package/com.macxrbridge.xr/Editor/CommandBridge.cs` (Editor command bridge: `.macxr/cmd/*.cmd` → `.macxr/out/*.out`, Console mirrored to `.macxr/unity.log`, `status.json`, commands `play/stop/refresh/menu/runtime/xr-standalone/hierarchy/sh/shbg`) and `scripts/runner.command` (shell queue in the Terminal). Lesson learned: **never run adb through the Unity bridge** (it blocks the Editor); adb only through the runner.

Fixes in the fork (branch `macxr-bridge`), in order of discovery:
1. `EntryPoint.cpp`: accept any API 1.1 patch version (OVRPlugin requests 1.1.61; the runtime was built against 1.1.57 and refused).
2. `EntryPoint.cpp`/`Instance.cpp`: advertise and fill in `XR_META_headset_id` (`MetaXRFeature` only turns on with a runtime that exposes this extension).
3. `Instance.cpp`: `runtimeName = "OXRSys Runtime for Meta Quest"` and `systemName = "Meta Quest 3"` (OVRPlugin rejects "Non-Oculus OpenXR runtime" based on the name).
4. `Session.cpp`: `xrGetReferenceSpaceBoundsRect(STAGE)` returns 3×3 m when the guardian hasn't arrived yet (instead of `XR_SPACE_BOUNDS_UNAVAILABLE`).
5. `EntryPoint.cpp`: advertise `XR_EXT_local_floor` (in addition to core 1.1 LOCAL_FLOOR).
6. **The decisive fix** — `InputManager.cpp`: before the first head pose, LOCAL sat on the floor (0,0,0), the same as LOCAL_FLOOR; Unity read LOCAL_FLOOR − LOCAL = 0, treated it as "unknown floor" and recreated the app space **every frame** (`OpenXRSession::Tick → HandleSetTrackingOriginMode → CreateLocalFloorSpaceEx`), and OVRPlugin's `xrEndFrame` pointed at the destroyed space (`XR_ERROR_HANDLE_INVALID`, zero frames). Default LOCAL now sits at eye height (0,1.6,0).
7. Temporary diagnostics still in the code: backtrace in `CreateReferenceSpace`, call `TRACE`, warnings in `EndFrame`. Remove before publishing.

Result: `ovrPluginInitialized = True`, session focused, `VideoEncoder: submit stereo frame srcL=1512x1680 srcR=1512x1680`, Quest 3 client connected (USB adb or Wi-Fi), tracking and hands arriving (`left hand active flags=0x71`), WaitFrame stable at 13.9 ms (72 Hz). Known open items: passthrough (`Failed to initialize Insight Passthrough`, `XR_FB_passthrough` missing), `EnvironmentRaycastManager` not supported, microgestures, anchors, PCA.

8. `HandTracker.cpp`/`EntryPoint.cpp`: advertise `XR_FB_hand_tracking_aim` and `XR_FB_hand_tracking_mesh`; fill in `XrHandTrackingScaleFB` (scale 1.0) and `XrHandTrackingAimStateFB` (pinch from thumb–fingertip distance, shoulder aim approximated from the palm); minimal `xrGetHandMeshFB` (26 joints, 0 vertices). Reason: the ISDK (`FromOVRHandDataSource`) only considers the hand connected when `HandScale > 0`; without it `HandVisual.IsVisible` stayed false and nothing showed up. Measured result: `Hand.IsConnected = true`, `IsVisible = true`, `IsPointerPoseValid = true`.
9. App (`hello-world`): `EditorKeyboardDriver` raised the rig to 1.6 m and tilted it 35° because it checked `XRSettings.isDeviceActive` in `Start`, before XR had started; it now waits up to 2 s and backs off if XR is active. This was the "scene on the floor" (camera at 2.57 m looking down). Measured afterwards: TrackingSpace (0,0,0), CenterEyeAnchor y = 1.19 m.

10. **Extended protocol** (`common/Protocol.h`, client `XrApp.cpp`, `TrackingReceiver.cpp`, `InputManager.*`): the client sent only each joint's position and ONE rotation for the whole hand → twisted fingers in the ISDK. It now sends the rotation of each of the 26 joints (int16 ×4, +416 bytes, flag `TRACKING_FLAG_HAND_JOINT_ROTATIONS_VALID`, compatible with older clients; `TestProtocolLayout` updated to 1592 bytes). `HandTracker::LocateHandJoints` now converts joints and the aim pose to the requested `baseSpace` (it used to ignore it; an upstream roadmap item).
11. Wi-Fi vs USB measured: Wi-Fi ABR dropped to 10 Mbps, ~21 ms frame age, 18–20 repeated frames/s (micro-stutters + flicker); USB 32–40 Mbps, ~11 ms, 1–3 repeated/s. The client only picks USB if the runtime (Unity in Play) is already up when it connects; otherwise it stays on Wi-Fi — restart the OXRSys app on the headset while Play is running.

Operational notes: the app's `Microphone.Start` freezes the Editor until macOS shows/receives the microphone permission for Unity (once). The Quest's USB (adb) authorization is lost when the adb server restarts; the client falls back to Wi-Fi (ABR at 10 Mbps, decode ~12 ms, frame age ~20 ms) — reauthorize on the headset and redo `adb reverse` to get USB back.

Unity project: Standalone XR Plug-in Management configured via `xr-standalone` (OpenXR loader + Meta XR Feature + Touch/Touch Plus/Hand Interaction; `runInBackground = true`). Unity registered in the Hub.

12. Local commits: `meta-vr` (`17e948c`, 553 files) and the `oxrsys` fork, branch `macxr-bridge` (`e329840`, `upstream` remote only). `HandRayTweaks.cs` (menu "Hello World ▸ MacXR Bridge ▸ Hand ray: long (1.5 m)") applied to the scene.

## Nov 8 (morning) — Step 2: real spatial anchors in Play Mode ("spatial" proxy)
17. **Proxy architecture** (`common/SpatialProtocol.h`, new): the Mac runtime has no tracking of its own, so every spatial function becomes a message on the `TcpRecordType::Spatial` channel (port 9948, USB) and the **Quest client executes it on the headset's own OpenXR**. `MsgHeader {version, kind, op, requestId, payloadSize}` + POD structs; synchronous `Request → Response` (blocks the app thread, 4 s timeout; mesh 10 s), `Event` for asynchronous completions (`XrEventData…CompleteFB/META`), `Poses` at 20 Hz with the pose of each remote space in the client's STAGE (= the runtime's "world" frame), `Hello` with `features` (0x1f = anchors, META persistence, scene, scene capture, mesh) and `scenePermissionGranted`.
18. **Runtime** (`SpatialProxy.h/.cpp`: transport, call correlation, pose cache, event queue; `SpatialEntity.h/.cpp`: the 21 functions of `XR_FB_spatial_entity`, `_storage`, `_query`, `_container`, `XR_META_spatial_entity_persistence`, `_discovery`, `XR_FB_scene`, `XR_FB_scene_capture`, `XR_META_spatial_entity_mesh`; `Space` gained `Type::Remote` + `ToWorldPose`; `Session::CreateRemoteSpace`; `DrainEvents` runs in `xrPollEvent` (app thread) to create the `XrSpace`s before delivering the events; `xrRetrieveSpace*Results` answer from a cache filled by the event — the client already fetches the results on the headset and sends them along). Caches for uuid/components (immutable), component status (500 ms, invalidated by SetStatus) and mesh (3 s, for the two-call idiom). `XrSystemSpatialEntityPropertiesFB.supportsSpatialEntity = true`.
19. **Quest client** (`SpatialBridge.h/.cpp`, `SpatialPermission.*`, `XrApp.*`, manifest, `NativeActivity.java`): enables the 9 extensions on the headset's instance; a reader thread on the spatial socket executes the requests, forwards events from `xrPollEvent`, sends the poses of tracked spaces (`xrLocateSpace` vs STAGE) at 20 Hz, validates every spaceId received (stale ids never reach Meta's runtime), and destroys its spaces on disconnect. Permissions `USE_ANCHOR_API` (install-time) and `USE_SCENE` (requested at runtime in `onCreate`, result via JNI `nativeSetScenePermission`). `CLIENT_CAPABILITY_SPATIAL_ENTITY/SCENE_CAPTURE` advertised.
20. **Test tool** (`MacXRBridge/Editor/AnchorTestTools.cs` + bridge commands `anchor x y z`, `anchors`, `anchor-save all|name`, `anchor-load uuid[,uuid]`, `anchor-erase nome`): cyan cube with `OVRSpatialAnchor`; load creates a yellow sphere via `LoadUnboundAnchorsAsync → LocalizeAsync → BindTo`.
21. **Measured result (08:11)**: `anchor 0.2 1.1 0.6` → runtime `xrCreateSpatialAnchorFB at (-0.22, 1.10, -0.35) -> 0` (pose converted from Unity's LOCAL_FLOOR to the Quest's STAGE), event `anchor create complete result=0`, `OVRSpatialAnchor.Created=True Localized=True Uuid=ad642124-…`; `anchor-save all` → `xrSaveSpacesMETA -> 0`, `SaveAnchorsAsync Success=True`. In other words, **real persistent anchors from the Editor on the Mac**. Known limitation: when the OXRSys app pauses (headset taken off), the client disconnects and destroys its spaces; `OVRSpatialAnchor`s already in Unity are orphaned (recreate them or reload by UUID), just as with Quest Link when it drops.
22. Hello World app: `LabelManager` now also anchors labels in the Editor when `OVRPlugin.initialized` (Quest Link, MacXR Bridge or Simulator); without a headset it behaves as before.
23. `ctest` only passes with Play stopped: Unity's streaming server holds ports 9944–9948 and the loopback tests fail ("tcp := true/false") — not a bug, just a port conflict.

## Nov 8 (morning) — Step 4 (part 1): Quest camera (PCA) relayed to the Editor — real frame on the Mac
29. **Decision**: the `XR_METAX1_passthrough_camera` extension (which `PassthroughCameraAccess`/native MRUK use in the Editor) is experimental and **has no public headers** — the "unchanged app" path can't be implemented without binary reverse engineering. Edson chose **a real relay + our own source**: the Quest captures the camera and the Editor reads the frames through a source of our own.
30. **Quest client** (`HeadsetCamera.java` + `CameraSender.*` + JNI): Camera2 opens the passthrough camera (`id=50`, vendor `camera_source=0`, `position=0` = left), `ImageReader` JPEG 640×480 @10fps; reads `LENS_INTRINSIC_CALIBRATION` (fx≈431, fy≈324, cx≈320, cy≈240) and `LENS_POSE_TRANSLATION/ROTATION` (extrinsics); each frame goes via JNI to `CameraSender`, which sends Hello + frames over the **camera channel (port 9949)** along with the frame's head pose. Permission `horizonos.permission.HEADSET_CAMERA` (granted with `adb pm grant`).
31. **Runtime** (`common/CameraProtocol.h`, `CameraRelay.h/.mm`, `StreamingServer` `TcpCameraThread`): receives the frames, decodes the JPEG with ImageIO (CoreGraphics), composes the camera's world pose (headPose × headFromCamera) and keeps the latest RGBA. Exposes it to Unity through C (`oxrsys_camera_connected`, `oxrsys_camera_get_latest` → `FrameInfo`), with default visibility (the rest of the dylib is hidden).
32. **Editor** (`BridgeCameraSource.cs` + `camera` command): resolves the symbols of the ALREADY loaded runtime via `dlsym(RTLD_DEFAULT, ...)` (bug fixed: the `dlopen(RTLD_NOW)` fallback loaded a 2nd copy of the dylib with a different `CameraRelay`, always "not connected"); copies the RGBA into a `Texture2D`, saves a PNG.
33. **Result (confirmed by Edson, PNG)**: the real Quest passthrough frame (desk, laptop, phone, monitor showing code) appeared in the Mac Editor — 640×480, frameId increasing (~1758), real camera intrinsics and pose. **The real Quest camera reaches Play Mode on the Mac without the proprietary extension.**
34. Remaining for step 4: wire the frames into the app's detection (feed `ObjectDetectionAgent`/`IDetectionSource` with the `Texture2D` + the camera pose), frame orientation/rectangle if needed, and the depth/raycast part (`XR_META_environment_depth`/`EnvironmentRaycastManager`).

## Nov 8 (afternoon, Edson away) — Step 4 (part 3): real detection working + depth relayed
38. **Why YOLO detected nothing in the Editor**: MRUK's `PassthroughCameraAccess.Update()`, in the Editor, pulls a CPU image from native MRUK (`CameraAcquireLatestCpuImage` — an Editor-only camera, at a different resolution) and calls `LoadRawTextureData` on the **same texture** we were injecting into: the model was getting striped garbage (saved to `.macxr/agent-tex.png` by `agent-test`). Fix: `BridgeCameraFeed` nulls out that delegate while the feed is on (and restores it on exit). This was also the source of the "surfboard" detections seen with the feed off.
39. **Result**: with the desk test image, `YOLO 1 caixa: laptop 0.36` every ~0.5 s → `PassthroughDetectionSource` projects → **a real "o notebook" label created by `LabelManager`** (with `fixed`, at 1.2 m). The whole camera → YOLO (Mac GPU) → ray → label chain works in Play Mode. It also runs with the live camera (with the headset sitting still off the head it produced "umbrella" over the whole scene — expected garbage for a scene with no objects from the vocabulary).
40. **Threshold**: in the dark the scores are low (laptop 0.36), and the app cuts off at 0.5 (agent/provider) and 0.45 (`LabelManager.minScore`). `camera-show … thr=0.3` lowers all three for the session only (the provider is a ScriptableObject: restored on exiting Play). On the headset this is app tuning, not a bridge concern.
41. **Reconnection always over USB**: when stopping/restarting Play, the Wi-Fi announcement arrived before the new USB attempt (1 s) and the client stayed on Wi-Fi — where there is no spatial/camera channel (`xrCreateSpatialAnchorFB without headset`, camera "disconnected"). The client now holds back Wi-Fi announcements for 2.5 s and tries USB right away. Verified: Play stop/start comes back over `usb_adb` with the camera.
42. **MRUK room "NoRoomsFound"**: the headset delivers a discovery in several events (20 + 0 + 2 spaces) before the app reads the first one; the runtime overwrote the batch and MRUK only saw the last one. Fixed in the runtime (per-request batch queue, for FB query and META discovery). **Built; takes effect after restarting Unity.**
43. **Environment depth relayed** (`XR_META_environment_depth`): the client creates the provider (with hand removal), acquires 5×/s, reads the left eye (320×320) on the GPU → `glReadPixels` → `uint16`, and sends it over the camera channel (`MsgKind::Depth`) with near/far, the view's pose and FOV, and the head pose at the same instant (STAGE). The runtime keeps the latest one and exports `oxrsys_depth_get_latest`. **Quest side verified** (320×320 provider, near 0.1, far ∞, frames at 5 Hz); runtime built, **requires restarting Unity**.
44. **Conventions verified with real data** (`depth_dump.bin` dump the client writes on the 5th frame of each start): row 0 = **bottom**, linear depth = near/(1−d) (infinite far).
